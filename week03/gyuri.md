### 4-1. abstract 키워드 - 추상 메서드와 추상 클래스
- **추상 메서드** : 선언부는 있는데 구현부는 없는 메서드
- **추상 클래스** : 추상 메서드를 하나라도 갖고 있는 클래스는 추상 클래스로 선언해야 함 (추상 메서드 없어도 선언 가능)

```java
동물 동물들[] = new 동물[3];
동물들[0] = new 쥐();
동물들[1] = new 고양이();
동물들[2] = new 강아지();

for (int i = 0; i < 동물들.length; i++) {
    동물들[i].울어보세요();
}
```

```java
package abstractMethod01;

public class 동물 {
	void 울어보세요() {
		System.out.println("나는 동물! 어떻게 울어야 하나요?");
	}
}
```

- 변수 `동물들[0]`의 타입은 동물이지만 실제로 가리키는 객체는 쥐 인스턴스
- 동물 타입의 참조 변수를 통해 하위 클래스의 인스턴스가 가진 메서드를 호출
  - 변수는 동물로 선언돼 있지만 호출되는 건 실제 객체(쥐)가 오버라이딩한 `울어보세요()` → **다형성**
- `동물들[i].울어보세요();`를 컴파일할 때, 컴파일러는 이 변수에 나중에 쥐가 들어올지 고양이가 들어올지 알 수 없음
  - 동물에 `울어보세요()`가 있으면 → 실행할 때는 실제 객체(쥐)의 오버라이딩된 메서드가 호출됨
  - 동물에 `울어보세요()`가 없으면 → 쥐에 그 메서드가 있어도 **컴파일 에러**

**두 가지 문제**
1. 동물 객체는 어떻게 울어야 하지? → 동물은 구체적인 동물이 아니라 울음소리를 정할 수 없음
   누가 실수로 `new 동물()`을 만들면 어떡하지?
2. 그렇다고 동물의 `울어보세요()`를 지울 수는 없음 → 하위 클래스가 오버라이딩할 `울어보세요()`가 동물 클래스에 있어야 함

⇒ 몸체를 채울 수도 없고, 메서드를 지울 수도 없음

**이 두 가지 문제가 추상 메서드와 추상 클래스로 한 번에 해결됨**
- `울어보세요()`를 **추상 메서드**로 선언 → 몸체 없이 호출용 자리만 남음
- 추상 메서드를 가진 클래스는 **추상 클래스**로 선언해야 함
  → 추상 클래스는 **인스턴스, 즉 객체를 만들 수 없는 클래스**가 됨 → `new 동물()` 하면 컴파일 에러

```java
abstract class 동물 { abstract void 울어보세요(); }

abstract class 포유류 extends 동물 { }   // 구현 안 함 → 대신 추상 클래스로 선언

class 쥐 extends 포유류 {
    void 울어보세요() { ... }             // 결국 여기서 구현해야 함
}
```

- 추상 메서드는 **하위 클래스에게 메서드 구현(오버라이딩)을 강제**함
  - 구현 안 하면 그 하위 클래스도 추상 클래스로 선언해야 함 (의무가 아래로 넘어감)
  - 객체를 만들 수 있는 클래스가 되려면 결국 반드시 구현해야 함

### 4-2. 생성자

- **생성자(객체 생성자 메서드)** : 클래스명과 이름이 같고 반환 타입이 없는 메서드, `new`로 객체 생성 시 호출됨
- 생성자를 하나도 안 만들면 → 컴파일러가 인자 없는 **기본 생성자** 자동 추가 (`동물() { }`)
- 생성자를 하나라도 직접 만들면 → 기본 생성자 자동 추가 안 됨

### 4-3. 클래스 생성 시의 실행 블록, static 블록
```java
public class 동물 {
    static {
        System.out.println("동물 클래스 레디 온!");
    }
}

public class Driver01 {
	public static void main(String[] args) {
		동물 뽀로로 = new 동물();
	}
}
// 동물 클래스 레디 온!
```

> **static 블록** : 클래스가 static 영역에 배치될 때 실행되는 코드 블록

- 동물 클래스를 쓰려면 먼저 static 영역에 올려야 하고, 그 순간 static 블록이 실행됨

```java
public class Driver02 {
	public static void main(String[] args) {
		System.out.println("main 메서드 시작!");
	}
}
// main 메서드 시작!

public class Driver03 {
	public static void main(String[] args) {
		System.out.println("main 메서드 시작!");
    동물 뽀로로 = new 동물();
  }
}
// main 메서드 시작!
// 동물 클래스 레디 온!
```
- **Driver02** : 동물 클래스를 안 쓰니까 로딩 안 됨 → static 블록 실행 안 됨
- **Driver03** : "main 메서드 시작!"이 먼저 찍힘 → 프로그램 시작할 때 미리 로딩되는 게 아니라 `new 동물()` 줄에 도달해서 **처음 사용될 때 로딩**됨

**static 블록 실행 중엔 객체가 하나도 없어서 객체 멤버에 접근 불가**
```
System.out.println("main 메서드 시작!");
   static 영역: [Driver03]            힙: (비어 있음)

동물 뽀로로 = new 동물();
   ① 동물 클래스 로딩
   static 영역: [Driver03] [동물]     힙: (비어 있음)   ← 이때 static 블록 실행!
   ② 객체 생성
   static 영역: [Driver03] [동물]     힙: [뽀로로 객체]
```
- 만약 동물에 `String 이름;` 같은 객체 멤버가 있어도 static 블록에서는 쓸 수가 없음

**동물 클래스의 인스턴스를 여러 개 만들어도 동물 클래스의 static 블록은 단 한 번만 실행됨**
```
static 영역: [동물 클래스]  ← 하나뿐, 처음 로딩될 때 static 블록 실행
힙: [뽀로로] [피카츄]      ← new 할 때마다 생성, 매번 생성자 실행
```

**클래스는 처음 사용될 때 로딩된다**
```java
public class 동물 {
    static int 개체수 = 0;                  // 1. 정적 속성

    static void 소개() {                    // 2. 정적 메서드
        System.out.println("나는 동물 클래스");
    }

    static {
        System.out.println("동물 클래스 레디 온!");
    }
}
```
1. 정적 속성 사용
```java
System.out.println(동물.개체수);
// 동물 클래스 레디 온!
// 0
```
2. 정적 메서드 사용
```java
동물.소개();
// 동물 클래스 레디 온!
// 나는 동물 클래스
```
3. 인스턴스 생성
```java
동물 뽀로로 = new 동물();
// 동물 클래스 레디 온!
```

### 4-4. final 키워드
| 대상 | 의미 |
|---|---|
| final과 클래스 | 상속을 허락하지 않겠다. 하위 클래스를 만들 수 없다. |
| final과 변수 | 변경 불가능한 상수가 됨. |
| final과 메서드 | 오버라이딩을 금지함. |

### 4-5. instanceof 연산자
> **instanceof 연산자** : 만들어진 객체가 특정 클래스의 인스턴스인지 물어보는 연산자 → `true` 또는 `false` 반납

```java
동물 펭귄객체 = new 펭귄();

System.out.println(펭귄객체 instanceof 동물);  // true
```
- `new 펭귄()`으로 만든 펭귄 객체를 동물 타입 변수에 담음 (**업캐스팅**)
- 객체 참조 변수의 타입이 아닌 **실제 객체의 타입**에 의해 (객체의 조상까지 포함해서) 처리

**instanceof 연산자는 클래스들의 상속 관계뿐만 아니라 인터페이스의 구현 관계에서도 동일하게 적용**
- 상속 관계 : `펭귄 extends 조류` → 펭귄은 조류의 한 분류이다
- 구현 관계 : `박쥐 implements 날수있는` → 박쥐는 날 수 있는 것이다
  - `박쥐객체 instanceof 날수있는` → true (박쥐는 날수있는을 구현함)
  - `박쥐객체 instanceof 박쥐` → true (실제 객체가 박쥐)

### 4-6. package 키워드
> package 키워드는 **네임스페이스**를 만들어줌

- 김규리의 iphone, 박서희의 iphone : iphone이라는 명칭은 갖지만 소유자는 각각이므로 이름 충돌이 발생하지 않음 → 이때 **소유자가 패키지**

### 4-7. interface 키워드와 implements 키워드
> 인터페이스는 **public 추상 메서드**(+ **default 메서드** (몸체 있는 메서드))와 **public 정적 상수**만 가질 수 있음

- 메서드에 `public abstract`, 속성에 `public static final`을 붙이지 않아도 자동으로 알아서 붙여줌
  - **public** : 인터페이스는 외부에 공개하는 약속이라 숨길 이유가 없음
  - **abstract** : 구현은 구현 클래스가 하는 거라 몸체가 없음
  - **static final** : 인터페이스는 객체를 못 만드니 객체 멤버를 가질 수 없음 → 정적 상수만 가능

### 4-8. this 키워드
> **this**는 객체가 자기 자신을 지칭할 때 쓰는 키워드

- **객체 변수**(클래스 안, 메서드 밖) vs **지역 변수**(메서드 안)
- 지역 변수와 속성(객체 변수, 정적 변수)의 이름이 같은 경우 **지역 변수가 우선**
  - 객체 변수를 사용하려면 → `this` 사용
  - 정적 변수를 사용하려면 → 클래스명 사용

### 4-9. super 키워드
> **super**는 바로 위 상위 클래스의 인스턴스를 지칭하는 키워드

- `super.super` 형태로 접근 불가능

```
뽀로로.method()                 ← 펭귄의 method()
 └ super.method()               ← 조류의 method()
    └ super.method()            ← 동물의 method()
       └ "동물" 출력
    └ "조류" 출력
 └ "펭귄" 출력
```


## SOLID. 응집도는 높이고, 결합도는 낮추라는 고전 원칙을 객체 지향의 관점에서 재정립**
- **결합도**가 낮으면 모듈 간의 상호 의존성이 줄어들어 객체의 재사용이나 수정, 유지보수가 용이함
- **응집도**가 높은 모듈은 하나의 책임에 집중하고(기능적 관련성) 독립성이 높아져 재사용이나 기능의 수정, 유지보수가 용이함

### 5-1. SRP - 단일 책임 원칙
> 어떤 클래스를 변경해야 하는 이유는 오직 하나뿐이어야 한다.

- 핵심 : **역할(책임)을 분리하라**
- 남자 클래스가 여자친구, 직장 상사, 어머니, 소대장 모두와 관계 → 너무 많은 역할과 책임을 짊어짐 → 변경해야 할 이유가 여러 개
  ⇒ 역할과 책임에 따라 네 개의 클래스로 쪼갬 (남자친구, 사원, 아들, 소대원)
- 사람 클래스에 군번 속성이 있다면? → 참조 변수 줄리엣이 가진 군번 속성에 값을 할당하는 코드를 제재할 방법 X
  ⇒ 사람 클래스를 남자 클래스와 여자 클래스로 분할하고 남자 클래스에만 군번 속성을 갖게 함
  - 남자 클래스와 여자 클래스에 공통점 없음 → 사람 클래스 제거
  - 공통점 많음 → 사람 클래스를 상위 클래스로 해서 공통점을 사람 클래스에 두고, 남자 클래스와 여자 클래스가 사람 클래스를 상속. 차이점만 각자 구현
- 모델링 과정을 담당하는 **추상화**와 관계 깊음
  - 애플리케이션의 경계를 정하고 추상화를 통해 클래스들을 선별하고 속성과 메서드를 설계할 때 SRP를 고려하라

### 5-2. OCP - 개방 폐쇄 원칙
> 자신의 확장에는 열려 있고, 주변의 변화에 대해서는 닫혀 있어야 한다.

- **상위 클래스 또는 인터페이스를 중간에 둠**으로써 달성
  - **자동차** 클래스를 중간에 둠 → 운전자는 자동차의 변화에 닫혀 있고(운전 습관 영향 X), 다양한 자동차는 자신의 확장에 열려 있음
  - **JDBC**를 중간에 둠 → 자바 애플리케이션은 데이터베이스라고 하는 주변의 변화에 닫혀 있고, 데이터베이스는 자신의 교체(확장)에 열려 있음
  - **목적 파일**을 중간에 둠 → 개발자가 작성한 소스코드는 운영체제의 변화에 닫혀 있고, 각 운영체제별 **JVM**은 자신의 확장에 열려 있음
- **유연성, 재사용성, 유지보수성**을 얻을 수 있음
- **스프링 프레임워크**는 OCP의 좋은 예

### 5-3. LSP - 리스코프 치환 원칙
> 서브 타입은 언제나 자신의 기반 타입으로 교체할 수 있어야 한다.

- 객체 지향에서의 상속은 조직도나 계층도가 아닌 **분류도**가 되어야 함
  - 하위 클래스 **is a kind of** 상위 클래스
  - 구현 클래스 **is able to** 인터페이스

```java
아버지 춘향이 = new 딸();  // 춘향이는 아버지형 객체 참조 변수이기에 아버지 객체가 가진 행위(메서드)를 할 수 있어야 하는데 아버지의 어떤 역할을 시킬 수 있을까?
동물 뽀로로 = new 펭귄();  // 동물의 행위(메서드)를 하게 하는 데 전혀 이상함이 없다
```
- 하위 클래스의 인스턴스는 상위형 객체 참조 변수에 대입해 상위 클래스의 인스턴스 **역할을 하는 데** 문제가 없어야 한다
```java
void 처리(계좌 a) { ... }   // 이 코드는 "계좌"의 약속만 믿고 짜여 있음

처리(new 계좌());
처리(new VIP계좌());        // 하위형을 넣어도 문제없어야 함
```

**1. 선행 조건 강화 X** : 메서드 호출 **전에** 호출하는 쪽이 지켜야 하는 조건
```java
class 계좌 {
    // 선행 조건: 금액 > 0
    void 출금(int 금액) { ... }
}

class VIP계좌 extends 계좌 {
    // 선행 조건: 금액 >= 10000  ← 강화됨 (요구가 까다로워짐)
    void 출금(int 금액) {
        if (금액 < 10000) throw new IllegalArgumentException();
        ...
    }
}
```
- "0보다 크면 된다"고 믿고 `a.출금(5000)` 호출 → VIP계좌면 예외 발생

**2. 후행 조건 약화 X** : 메서드가 끝난 **후에** 보장해주는 결과
```java
class 계좌 {
    // 후행 조건: 입금 후 잔고가 금액만큼 늘어남
    void 입금(int 금액) { 잔고 += 금액; }
}

class 수수료계좌 extends 계좌 {
    void 입금(int 금액) { 잔고 += 금액 - 500; }   // 보장이 줄어듦 ← 약화됨
}
```
- 10000원 입금하면 잔고가 10000원 늘 거라 믿었는데 9500원만 늘어남

**3. 불변 조건 유지** : 객체가 살아 있는 동안 **언제나** 참이어야 하는 성질
```java
class 계좌 {
    int 잔고;   // 불변 조건: 잔고 >= 0
}

class 마이너스통장 extends 계좌 {
    // 잔고가 -100만까지 가능  ← 불변 조건 깨짐
}
```
- "잔고는 음수가 아니다"를 믿고 짠 코드가 마이너스통장에서 이상하게 동작

### 5-4. ISP - 인터페이스 분리 원칙
> 클라이언트는 자신이 사용하지 않는 메서드에 의존 관계를 맺으면 안 된다.

- 남자 클래스를 토막 내는 것이 아니라, 여자친구를 만날 때는 **남자친구 역할만** 할 수 있게 인터페이스로 제한
- 같은 문제에 대한 두 가지 다른 해결책 : **단일 책임 원칙(권장)**, 인터페이스 분리 원칙
  - SRP : 남자 클래스를 역할별 클래스로 **쪼갬**
  - ISP : 남자 클래스는 그대로 두고, 상대에 따라 **인터페이스로 제한**
- **상위 클래스는 풍성할수록 좋다**
  - 하위 클래스들의 공통 속성/메서드는 상위 클래스로 올림
  - 상위 타입 변수로 캐스팅 없이 사용 가능, 다형성 활용 가능, 중복 제거
  - 빈약하면 공통 기능인데도 매번 형변환 필요 → 다형성을 못 살림

```java
// 빈약한 상위 클래스
class 사람 { String 이름; }                       // 공통 기능이 없음

class 학생 extends 사람 { void 먹다() { ... } }
class 군인 extends 사람 { void 먹다() { ... } }

사람 김학생 = new 학생();
사람 이군인 = new 군인();

김학생.먹다();            // 컴파일 에러: 사람 타입엔 먹다()가 없음
((학생) 김학생).먹다();   // 다운캐스팅해야 호출 가능
((군인) 이군인).먹다();
```

```java
// 풍성한 상위 클래스
class 사람 { String 이름; void 먹다() { ... } }   // 공통 기능을 올림

사람 김학생 = new 학생();
김학생.먹다();            // 캐스팅 없이 호출
```
- 호출 가능 여부는 **변수 타입**, 실제 실행되는 메서드는 **인스턴스 타입**이 결정

- **인터페이스는 작을수록 좋다** → **인터페이스 최소주의 원칙**

### 5-5. DIP - 의존 역전 원칙
> 자신보다 변하기 쉬운 것에 의존하지 마라.

- 자동차가 구체적인 타이어들(스노우 타이어, 일반 타이어, 광폭 타이어)이 아닌 **추상화된 타이어 인터페이스**에만 의존
  → 다른 타이어로 변경돼도 자동차는 그 영향을 받지 않음 → **개방 폐쇄 원칙과 연관**
- 자동차는 자신보다 변하기 쉬운 스노우 타이어에 의존하던 관계를, 중간에 추상화된 타이어 인터페이스를 추가해 두고 **의존 관계를 역전**시킴
- 자신보다 변하기 쉬운 것에 의존하던 것을 추상화된 인터페이스나 상위 클래스를 두어 변하기 쉬운 것의 변화에 영향받지 않게 하는 것
- **상위 클래스일수록, 인터페이스일수록, 추상 클래스일수록** 변하지 않을 가능성이 높음
  - Ex. JDBC

### 5-6. 정리 - 객체 지향 세계와 SOLID
> **SoC (관심사의 분리)** : 관심이 같은 것끼리는 하나의 객체 안으로 또는 친한 객체로 모으고, 관심이 다른 것은 가능한 한 따로 떨어져 서로 영향을 주지 않도록 분리하라는 것

- 하나의 속성, 메서드, 클래스, 모듈, 패키지에는 **하나의 관심사**만 들어 있어야 한다
- SoC를 적용하면 **SOLID에 도달**함
- SOLID 원칙을 적용하면 소스 파일의 개수는 더 많아지는 경향 < 적용함으로써 얻는 혜택 (**논리 분할, 이해 쉬움, 개발 쉬움, 유지 관리 보수 쉬움**)
- 객체 지향은 현실 세계를 **모델링**함 → SOLID는 현실 세계 같아야 한다는 요건보다는 모델링을 통해 **추상화**됐다에 초점
