# 6장 - 스프링이 사랑한 디자인 패턴

디자인 패턴은 결국 객체지향의 기본 요소인 **상속, 인터페이스, 합성**을 이용해 문제를 해결한다.

합성은 다른 객체를 속성으로 가지고 참조해서 사용하는 방식이다.

---

## 01. 어댑터 패턴

서로 맞지 않는 인터페이스 사이에 변환기를 두어 연결하는 패턴이다.

### Spring에서는

`HandlerAdapter`가 대표적이다.

Spring MVC에는 요청을 처리하는 방식이 서로 다른 핸들러들이 있을 수 있다.

`DispatcherServlet`이 각 핸들러의 호출 방법을 전부 알 필요 없이,

```text
DispatcherServlet
→ HandlerAdapter
→ 실제 Handler
```

처럼 `HandlerAdapter`가 중간에서 호출 방식을 맞춰준다.

즉 **서로 다른 호출 방식을 하나의 공통 흐름으로 연결해주기 때문에 어댑터 패턴**이다.

---

## 02. 프록시 패턴

실제 객체 앞에 대리 객체를 두고, 호출 전후에 접근 제어나 부가 기능을 처리하는 패턴이다.

### Spring에서는

`@Transactional`이 대표적이다.

개발자가:

```java
@Transactional
public void order() {
}
```

라고 하면 실제 메서드가 바로 호출되는 것이 아니라 프록시가 먼저 호출을 받는다.

```text
호출
→ Spring Proxy
→ 트랜잭션 시작
→ 실제 order()
→ commit 또는 rollback
```

즉 **실제 서비스 앞에 대리 객체가 서서 트랜잭션 처리를 대신하기 때문에 프록시 패턴**이다.

---

## 03. 데코레이터 패턴

기존 객체를 감싸면서 기능을 추가하는 패턴이다.

### Spring에서는

기존 객체를 감싼 뒤 추가 기능을 덧붙이는 구조에서 사용된다.

```text
기존 기능
+ 추가 기능
```

즉 **원래 기능은 유지하면서 객체를 감싸 기능을 덧붙인다는 점에서 데코레이터 패턴**이다.

---

## 04. 싱글턴 패턴

하나의 클래스에 대해 하나의 인스턴스를 만들어 공유하는 패턴이다.

```text
private 생성자
static 단일 객체 참조 변수
static getInstance()
```

구조를 가진다.

### Spring에서는

Spring Bean의 기본 스코프가 `singleton`이다.

예를 들어 `@Service`로 등록한 객체를 사용할 때마다 새로 만드는 것이 아니라, Spring 컨테이너가 하나 생성해두고 공유한다.

```text
Spring Container
→ OrderService 하나 생성
→ 여러 곳에서 같은 Bean 사용
```

즉 **하나의 객체를 공유한다는 점에서 싱글턴 패턴과 연결된다.**

---

## 05. 템플릿 메서드 패턴

상위 클래스가 전체 실행 순서를 정하고, 일부 단계만 하위 클래스가 구현하는 패턴이다.

```text
템플릿 메서드
→ 전체 실행 순서

추상 메서드
→ 자식이 반드시 구현

훅 메서드
→ 필요할 때만 오버라이드
```

### Spring에서는

Spring의 여러 추상 클래스가 전체 처리 흐름을 정해두고, 개발자가 필요한 일부 메서드만 오버라이드하도록 한다.

```text
Spring
→ 전체 흐름 결정

개발자
→ 일부 단계만 구현
```

즉 **공통 흐름은 상위 클래스가 가지고 세부 단계만 바꾸게 하기 때문에 템플릿 메서드 패턴**이다.

---

## 06. 팩터리 메서드 패턴

어떤 객체를 생성할지 하위 클래스에 맡기는 패턴이다.

상위 클래스는 객체가 필요하다는 사실만 알고, 구체적으로 어떤 객체를 만들지는 하위 클래스가 결정한다.

### Spring에서는

Spring에서는 애플리케이션 코드가 직접 모든 객체를 `new` 하는 대신, Bean이나 객체의 생성 책임을 컨테이너나 Factory 쪽에 맡기는 구조가 사용된다.

```text
애플리케이션
→ 객체 필요

Spring
→ 객체 생성
→ 반환
```

즉 **객체 생성 책임을 사용하는 쪽에서 분리한다는 점에서 팩터리 계열 패턴과 연결된다.**

---

## 07. 전략 패턴

바뀔 수 있는 동작을 별도의 전략 객체로 분리하고, 필요한 전략을 선택해 사용하는 패턴이다.

```text
Context
Strategy
Concrete Strategy
Client
```

로 구성된다.

### Spring에서는

같은 인터페이스의 여러 구현체를 만들고, 필요한 구현체를 DI로 주입할 수 있다.

```text
PaymentGateway
├─ TossPayment
└─ KakaoPayment
```

`OrderService`는 `PaymentGateway`만 알고 실제 구현체는 주입받는다.

즉 **동작을 구현체로 분리하고 필요에 따라 갈아끼울 수 있기 때문에 전략 패턴과 연결된다.**

---

## 08. 템플릿 콜백 패턴

전략 패턴과 비슷하지만, 전략을 별도의 구현 클래스로 만들지 않고 익명 내부 클래스 등의 형태로 전달하는 패턴이다.

### Spring에서는

`JdbcTemplate`이 대표적이다.

Spring이:

```text
DB 연결
예외 처리
자원 정리
```

같은 공통 처리를 담당하고, 개발자는 실제로 수행할 DB 작업만 전달한다.

```text
Spring의 공통 흐름
→ 개발자가 넘긴 작업 실행
→ 공통 마무리
```

즉 **공통 흐름은 템플릿이 담당하고, 달라지는 부분만 콜백으로 넘기기 때문에 템플릿 콜백 패턴**이다.
